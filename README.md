# WhatsApp 实时翻译扩展（中印互译）

Chrome 扩展：WhatsApp 网页版消息实时翻译，**印尼语 ↔ 中文** 双向。
- 收到的外语消息 → 气泡下方插入**中文**译文
- 自己发出的中文 → 气泡下方插入**印尼语**译文（方便对方核对）
- 输入框右下角「译」按钮 → 把你打好的中文**直接替换进输入框**变成印尼语（再点一次还原原文），不自动发送
- 翻译走 **OpenAI 兼容的 LLM API**（Base URL / Key / Model 全部在设置页填，支持任何兼容服务商）
- 本地缓存去重：重复消息不重复计费

## 安装（3 分钟）

1. 把本文件夹整个复制到你要用的电脑上（不要解压到临时目录）。
2. Chrome 地址栏输入 `chrome://extensions`，打开右上角**开发者模式**。
3. 点**加载已解压的扩展程序**，选择本文件夹。
4. 工具栏出现蓝色「文A」图标即安装成功。

## 配置

1. 点工具栏图标，填写：
   - **API Base URL**：默认 `https://api.scnet.cn/api/llm/v1`（已内置，不用改）
   - **API Key**：你的 key（只存在本机浏览器 `chrome.storage.local`，不上传）
   - **模型**：默认 `Qwen3.8-Flash`（scnet 上实测可用）；换模型名须是所选 Base URL 服务支持的、支持 chat/completions 的任意模型
2. 点**测试连接** —— 显示「✔ 连接成功」才继续。
3. 打开 [web.whatsapp.com](https://web.whatsapp.com) 扫码登录，聊天里的消息下方会出现「译」色块。
4. 「启用自动翻译」开关可随时全局停用（气泡下方已显示的译文保留）。

## 工作原理 / 目录

| 文件 | 职责 |
|---|---|
| `manifest.json` | MV3 清单；权限仅 `storage` + 翻译 API 域名的 fetch 能力 |
| `background.js` | service worker：攒批(350ms 窗口)→ 调 LLM → 缓存(LRU 2000 条)；批量失败自动逐条降级重试 |
| `content.js` | 页面扫描（MutationObserver + 2s 兜底轮询）、译文行注入、输入框反向翻译按钮 |
| `content.css` | 注入样式（收=蓝色系 / 发=绿色系，失败=粉红可点击重试） |
| `popup.html/js` | 设置页：填 key、测试连接、开关、清缓存 |

## WhatsApp 改版后失效怎么办

WhatsApp 前端类名是混淆的、会定期变。v1.1.2 起扫描器自带三层防线：
1. **扫描根自动回退**：`#main` → `role="application"` → `body`（自动排除侧栏/标题/输入区）——实测 2026 版 WhatsApp 中 `#main` 存在但聊天区不在其内部，旧版在此直接扫 0 条。
2. **选择器阶梯**：`[data-id]` 气泡（跨版本稳定属性，`true_/false_` 前缀自带收发方向）∪ 旧版 `copyable-text/selectable-text` → 结构特征 `span[dir="auto"]` 兜底。
3. **popup「诊断」按钮**：显示扫描根/策略/命中数/失败数/DOM 锚点统计/首个气泡 HTML 样本。**不翻译时先点诊断**，把结果截图发给维护者即可定位，无需猜。

若仍失效：F12 控制台看 `[wTranslate]` 报错；诊断里 `sample` 字段就是真实消息节点的 HTML，按它的结构在 `content.js` 的 `SCAN` 段加一条选择器即可。

## 常见问题

**译文一直显示「翻译中…」不出结果？** v1.1.3 已修复三大成因：
批量一次塞太多条（现在自动按 12 条/组切分并发）、后台批量失败后串行逐条重试（现在并行 3 路、单条 12s 超时）、响应通道丢失（现在 90s 兜底显示「点击重试」）。
若仍出现：等 1~2 分钟（首次大批量），或点击「⚠ 翻译失败（点击重试）」行手动重试；也可把模型换成响应更快的（如非思考模式的轻量模型）。

- **所有气泡显示 ⚠ 未配置 API Key**：先点扩展图标保存配置。
- **⚠ 401/403/429**：key 无效 / 欠费 / 限流。换 key 或稍后自动重试（点失败行重试）。
- **输出被模型带上了多余解释**：极少见；把 temperature 调到 0 或在系统提示词（`background.js` 的 `SYSTEM_PROMPT`）里再加一条硬约束。
- **想同时给英文/印尼文都翻**：当前自动判定为「含中文→印尼语，否则→中文」；改 `detectTarget()` 即可扩展。
- **隐私**：仅消息文本发往你配置的 API 服务商，与 WhatsApp 官方无关；WhatsApp 账号、聊天列表一概不读取。
- **host 权限已收紧为 `https://api.scnet.cn/*`**：默认服务商写死在扩展里，弹窗里改 Base URL 只能填 api.scnet.cn 域名的地址。若要换其他服务商（如 OpenAI），需自己在 `manifest.json` 的 `host_permissions` 里加上对应域名再重新加载扩展。

### 长消息只翻译了一部分 / 译文没有换行？（v1.1.4 已修复）

v1.1.4 起多行消息（如设备故障报告 `LAPORAN KERUSAKAN`）会**整段翻译并保留原有换行**，译文字体也放大到 15px。如果你还在旧版本上看到"只翻一行"，请按下方步骤更新到 v1.1.4。

### 厂内术语翻译不对？专属词典（v1.1.8）

弹窗 → 「**专属词典**」展开，每行一个术语，格式 `印尼文 = 中文`（`:` `：` 也可以）：

```
calender = 压延机
emboss = 压花辊
bahan baku = 原材料
```

点「保存词典」立即生效。**双向自动生效**：对方印尼文消息里的 calender 强制译成
"压延机"；你打"压延机"发出去，反向翻译强制用 calender。三层保障：
术语表注入模型提示词（含大小写说明）+ 模型输出整词硬替换兜底 +
改词典后旧译文缓存自动失效重译（不用手动清缓存）。
真实 scnet Qwen3.8-Flash 实测：`Mesin calender A06 rusak` → 「A06压延机坏了」。

**相近词不混（v1.1.9）**：词典里同时有 `mixing = 轧轮机` 和 `mixer = 混合桶`
这类只差一两个字母的术语时，替换按**整词精确匹配 + 两轮占位符**执行，
双向互不顶替。实测 `Mixing dan mixer keduanya jalan` → 「轧轮机和混合桶都在运行」，
「轧轮机和混合桶都要保养」→ "mixing dan mixer keduanya perlu perawatan"。
拼写变体（如 emboss vs embos）视为不同词、不自动归并——需要的话各加一行。

**v1.1.10**：若模型把 mixing 错译成 mixer 的中文（相近词摇摆），后台会用源文核对
自动纠正；同时翻译缓存升级重编，旧错误译文一次性作废。如果个别消息还显示旧错译，
点弹窗「清空翻译缓存」再刷新页面即可。

**v1.1.11**：①每条译文行右上角有灰色小水印（如 `v1.1.11`）——更新后先看一眼它，
就知道装没装上。②新增"一词之差"纠正：词典 emboss=压花辊，模型写成"压花轮"
（辊/轮同形）也会被强制改回；有歧义时不臆改。实测原句
`Heater emboss mohon di agendakan besok` → 「压花辊加热器请安排在明天，因为机器停机」。

**v1.1.12**：多行消息改为**按行对齐逐行核对术语**。之前整段核对时，一条消息里同时
出现 mixing 和 mixer（或任何两行的译文互相顶替）会让纠正层误判"译文合法"而弃权——
模型恰恰把 A 行的术语错译成 B 行的词。现在每行只拿本行源文核对，混淆必抓。
同值拼写变体（bambury/banbury 都=万马力）互认、不臆改。

**v1.1.13**：①输入框「译」按钮修复——以前必须先选中文字再点，因为点按钮会让输入框
失焦、WhatsApp 立刻把旧文字刷回来。现在**一次点击直接生效**，再点还原。②文件/状态
图标的内部名称（`wds-ic-read`、`ic-error`、`document-PDF-icon` 这类）不再被当成
消息正文送去翻译。

**v1.1.14**：输入框译文不再叠加在原文后面（如「早上好Selamat pagiSelamat pagi」）。
WhatsApp 新版输入框是 Lexical 编辑器，插入位置由它的「内部选区」决定，而内部选区要等
一个异步同步周期才跟上我们设的全选——以前同一拍里插入命中旧光标（文字末尾），译文被
**追加**。现在写入前「全选→等选区同步→再全选→插入」并校验结果，失败自动清空重插，
快速连点也不累积。

**v1.1.15**：①「🚫 这条消息已删除」这类系统占位消息不再翻译。②回复/引用消息顶部的
「~ 人名 +电话号」引用头行剥离、绝不作为正文送译——修复截图中删除消息/纯图片消息被
译成发送者人名的问题；消息带真实正文时只翻译正文。

**v1.1.16**：修复「绿色译文翻译的是群成员昵称，不是消息内容」。群里每条消息顶部的发送者
自定义昵称横幅（如 `~utamakan sholat` + 电话号）以前因比图注长而被当成正文送译——
`Scaner a08.`/`Suhu D005` 这类图注反而没有译文。现在取词阶段逐行剥离等于发送者名的行
（含 `~` 前缀），图注/正文正常翻译，昵称永不送译、也不进 API 请求（零计费）。

**v1.1.17**：彻底根治「绿色译文 = 群成员昵称」。v1.1.16 靠逐字比对发送者名剥离，
但真实 WhatsApp 的昵称横幅是独立消息块（`~utamakan sholat` + 电话号自成一块，`~` 后
无空格、名字裹方向控制符、带括注后缀），比对不上照样送译（截图里的「优先礼拜」「好的
（Fauzan & farlin）」）。现在改为结构性规则：凡以 `~` 开头的短行（`~` 后接数字的
「~2 jam＝约2小时」类正文除外）一律视为昵称横幅，永不翻译、不进 API。已按截图 1:1
复现验证：横幅零输出，图注 `Suhu D004/D005`、`Scaner a08` 正常出译文。

**v1.1.21**：修复配置列表两个问题：①旧版点「＋ 新增」或下拉切换时，会把**未保存的表单改动
静默写回旧配置**——导致两条配置最终存了同一个模型名，表现为「切换配置后模型名称不变」
（红→绿测试 test_popup.js S1 复现并修复）；②切换现在只读已保存值，丢弃未保存改动时弹出 ⚠
警告；下拉框中「● 」前缀标记当前翻译在用的配置；切换成功的提示行显示生效的模型名。

**v1.1.20**：设置页支持**多套模型配置列表**。可保存多个 API（名称+Base+Key+模型+温度），
下拉框随时切换，选中的那条**立即**用于翻译（无需保存/刷新）；「＋ 新增」复制当前参数建新条，
「删」移除。旧版单配置自动迁移为「默认配置」，Key 不丢。测试连接按当前表单实测。

**v1.1.19**：新增每行译文旁的 **⟳ 刷新按钮** + 「原文回显」防护。模型偶尔把输入原样吐回
（网关抽风/批量截断），旧版会当成译文显示并缓存，看起来就是「译文=原文」。现在：译文与
原文归一化相同 → 判为失败，行内显示 ⚠ 不再原样回显；该失败不会被缓存，点 **⟳** 即清除
该条缓存并强制重译（点击 ⚠ 行本身也可重试）。持续失败只重试一次不累积译文行；旧缓存里的
回显脏数据下次命中时自动重译（自愈）。水印 `译 v1.1.19`。

**v1.1.18**：昵称横幅过滤改为「电话号结构」规则，不再依赖 `~` 字符。v1.1.17 按 `~` 前缀
匹配在真实 WhatsApp 上仍失效——`~` 实际是独立 span 渲染，抽取到的名字文本
（`utamakan sholat`）根本不含 `~`；且真实电话号码用 U+2011 不间断横杠，旧的电话正则
也认不出。现在：横幅泡必含电话行（U+2011 已补进匹配），且横幅永不在 `[data-pre-plain-text]`
正文容器内——两条同时命中 → 整泡不译，与名字怎么写（括注、数字、`~` 分离）无关。
正文、图注（有 pre 容器）、vCard、`~2 jam` 类真实消息均不受影响。
测试夹具新增 X14/X15/X16 三种真实形态（`~` 独立 span、U+2011 电话、数字名），
先证明 v1.1.17 代码在这三条上翻出「优先礼拜/好的（Fauzan…/darman nidar23」（红），

### 名片/图片消息还在翻人名？（v1.1.7 已修复）

v1.1.6 靠 `data-pre-plain-text` 元数据识别发送者名，但**联系人名片**（名字行 + 电话行
各占一个 span）在很多版本里没有该元数据，且 jsdom 测试夹具与真实 Chrome 的 title 属性
路径结构不同 → 名字仍被翻。v1.1.7 补结构规则：

- 候选文本中**任何一行像电话号码**（`+62 813-...`、6 位以上数字）→ 判定为名片形态，
  电话行连同其上方的人名行一并剥离，整条不译；
- 单行候选**符合人名形态**（2–5 个首字母大写的词）且所在气泡**含图片/画布媒体**、
  又**不在正文容器内** → 判为名片名/媒体上方标签，跳过；
- 正常消息正文（句子形态、带标点/数字混合）不受影响，e2e 夹具 Z7 + 真 Chrome 验证。

### 发图片/贴贴图/名片消息，把人名也翻译了？（v1.1.6 起修复，v1.1.7 完善）

v1.1.5 在「图片/贴纸/联系人名片」这类**没有文字正文**的消息里，把唯一可见的文字
（群发送者名、电话号码）当成消息送译。v1.1.6 起：

- 用稳定属性 `data-pre-plain-text`（WhatsApp 给每条消息正文挂的「[时间] 名字: 」元数据）
  识别发送者名；候选文本恰好等于人名 → 整条不译，首行是人名 → 剥离后只译正文；
- 纯电话号码（`+62 813-2550-6131`）不再送译；
- 「晚上6:44 / 早上7:00」等全部中文时间戳补齐识别（原正则漏「晚上」）；
- 会话列表兜底加固：`#pane-side` id 失效时，用「listitem 内含可拖拽头像」识别侧栏，
  群名/最后一条消息预览一律不翻；
- **译文颜色改为绿色**（WhatsApp 品牌绿 `#25d366`，深色/浅色主题均可读）。

### 翻译速度慢？（v1.1.5 极速模式）

v1.1.5 默认开启**极速模式**：给 LLM 请求附加 `enable_thinking:false`，关闭推理模型的"思考链"。
在 scnet Qwen3.8-Flash 实测：8 条消息一批 **11.5s → 3.5s**（约 3.3 倍）。
弹窗里有「极速模式」复选框（默认勾选）。若你的服务商网关不认识该参数，扩展会自动剥离重试并记住，不会报错。
翻译结果本身有缓存，**重复消息零等待**；同一条消息永远只调用一次 API。
